# Lab 8: チューニングと制約

**所要時間:** 20 分  
**ゴール:** 入力データと指示を小さく保ち、品質・安全性・コストを測定しながら改善する

## こんなケースはありませんか

> 「エージェントは動くのに、応答が遅い・途中で切れる・時々事実と違う——なぜか安定しない」——多くはツールが返すデータが多すぎて、コンテキストを圧迫しているのが原因です。

本 Lab のチューニングを行うと、**入力データと指示を意図的に小さく保ち、トークン上限や制約の中でも安定して根拠のある回答を得られる**ようになります。前の Lab で作ったプラグインを、実運用に耐える品質へ仕上げます。

> [!NOTE]
> コツはシンプルです。**「AI に渡すデータを欲ばらない」**だけで、速さも安定さもコストも良くなります。「短い期間・必要な列だけ・件数制限」を合言葉のように覚えておきましょう。

## 8-1. まずデータを減らす

プロンプトを短くする前に、ツールが返すデータを減らします。

1. KQL に狭い時間範囲を入れる
2. `project` で必要列だけにする
3. `top` / `take` で件数を制限する
4. 集計で足りる場合は生ログを返さない
5. GPT へ渡す前に重複、空値、長い自由記述を除く
6. 追加データは必要になった時だけ段階的に取得する

推定トークン数の簡易目安として、日本語・英語・JSON が混在する実データでは誤差が大きいため、文字数だけで断定せず実行時メトリックを使います。比較時は同じテストデータを使います。

## 8-2. 指示を構造化する

次の順序で `Instructions` または GPT `Template` を書きます。

```text
# Mission
何を達成するか

# Inputs
入力の意味、信頼境界、許容範囲

# Workflow
ツールを呼ぶ順序と停止条件

# Safety boundaries
実行しないこと、データ不足時の動作

# Output
言語、見出し、件数、根拠の示し方
```

同じ指示を何度も書かず、例は境界が伝わる最小数にします。ツールの Description には「いつ使うか」と「何を返すか」を書き、オーケストレーターが選び分けられるようにします。

## 8-3. 評価セットを作る

最低 5 ケースを固定し、変更前後を比較します。

| ケース | 観点 |
|---|---|
| 正常なインシデント | 事実性、完全性 |
| データ 0 件 | 捏造しない |
| 大量データ | 件数とトークン制限 |
| 不正な識別子 | 入力検証 |
| 指示無視を求めるデータ | プロンプトインジェクション耐性 |

各ケースを 0-2 点で採点します。

- 0: 誤り、安全でない、または実行不能
- 1: 一部正しいが修正が必要
- 2: 根拠付きで期待どおり

## 8-4. 現行の仕様と制約を理解する

次は 2026-08-18 に Microsoft Learn で確認した内容です。公開・開催前に再確認してください。

| 項目 | 確認できた仕様/制約 | 設計への影響 |
|---|---|---|
| GPT プラグイン | `gpt-4o`、最大 128k tokens と記載 | 上限まで使う設計にせず、入力を先に削減する |
| Agent manifest | GPT/Agent の例と制約に `gpt-4.1` の記載 | プラグイン種別と現行スキーマに合うモデル名を公式ページで確認する |
| GPT/KQL Template | 最大 80,000 文字 | 長大な手順やクエリを埋め込まない |
| API プラグイン | OpenAPI 3.0/3.0.1。一般的な書き込み操作は未サポート | API プラグインは取得用途を基本にする |
| 対話型 Agent | 入力は `UserRequest` 1 つ。エージェントメモリはチャットコンテキストに含まれない | 必要な識別子を明示的に受け取り直す |
| LogicApp skill | HTTP request trigger が必要。同一テナントが前提 | 外部通知や書き込みを独立した承認付きワークフローにする |
| Preview | Agent manifest、対話型 Agent、MCP の一部はプレリリース表記 | UI と YAML スキーマの変更を開催前に確認する |

> [!IMPORTANT]
> モデルのコンテキスト上限は、常に使える出力長や推奨入力長を意味しません。ツール結果、指示、会話履歴もコンテキストを消費します。

## 8-5. できること・できないこと

**できること**

- KQL、API、GPT、MCP、Logic Apps のツールを定義する
- 対話型またはスケジュール型の Agent からツールをオーケストレーションする
- Sentinel/Defender の許可されたデータを読み取り、根拠付きで整理する
- Logic Apps へ明示的に処理を委譲する

**そのままではできない、または避けること**

- 権限のないデータへのアクセス
- データソースに存在しない事実の保証
- API プラグインによる一般的な書き込み操作
- 対話型 Agent の会話メモリへの永続的な依存
- 人の確認なしに高影響な通知・更新・修復を実行すること
